# How：架构与实现方案

## 系统边界

```text
                         GitHub OAuth / App
                                  │
                        ┌─────────▼─────────┐
编辑者 / 发布者 ───────▶│ Decap CMS / 管理 UI │
                        └─────────┬─────────┘
                                  │ GitHub API
                                  ▼
Git / 其他客户端 ───────────▶ GitHub 私有仓库
                                  │
                         Webhook + 定时校准
                                  ▼
                        ┌───────────────────┐
                        │ 自研同步与控制服务 │
                        │                   │
                        │ 仓库同步           │
                        │ 内容校验与索引     │
                        │ 部署编排           │
                        │ 分发任务与审计     │
                        └───┬───────────┬───┘
                            │           │
                     构建与部署       适配器 + 任务队列
                            │           │
                            ▼           ▼
                         公开网站     外部内容平台
```

自研服务不通过浏览器暴露 SSH，也不把服务器工作区作为正文事实源。Decap 使用 GitHub API，部署同步使用 SSH，两条通道分别授权。

## 逻辑模块

| 模块 | 职责 | 不负责 |
| --- | --- | --- |
| Public Site | 渲染公开文章、分类、标签、RSS | 在线编辑、平台任务 |
| Decap Admin | 内容表单、基础编辑、媒体与 Git 提交 | 部署状态、多平台任务 |
| Repository Connector | 校验仓库身份、获取指定 commit、维护受控工作区 | 解释发布状态 |
| Content Pipeline | 扫描、解析、校验、生成稳定内容快照 | 调用第三方平台 |
| Deployment Coordinator | 构建、发布、保留旧版、记录部署 | 编辑正文 |
| Distribution Coordinator | 生成任务、调度、重试、记录结果 | 保存平台凭据明文 |
| Platform Adapter | 平台格式转换及远端操作 | 决定文章是否应在主站发布 |
| Control API / UI | 状态查询、显式发布操作、重试和审计 | 绕过 Git 修改正文 |
| State Store | 索引、映射、任务、部署和审计记录 | 替代 Git 正文 |

## 仓库协议

内容仓库协议 v1 使用以下布局：

```text
content/
  <category>/
    <article>/
      index.md
      assets/
metadata/
  webpub.yml
  categories.yml
  platforms.yml
  redirects.yml
```

文章 Front Matter 是文章级元数据的唯一保存位置，包括稳定 ID、标题、slug、生命周期、发布时间和分发意图。中央 metadata 只保存仓库默认值、分类、平台目标和重定向，不复制逐篇文章字段。平台凭据存放在服务端密钥存储中。

完整目录、字段、状态和迁移规则见 [内容仓库与 Metadata 设计](content-repository.md)。校验器先识别 `schema_version`，再执行对应校验或拒绝不兼容内容，避免字段变更被静默误读。

## 内容标识与地址

- 首次导入时为缺少 ID 的文章生成唯一 ID，并通过一次显式迁移提交写回。
- 文章路径不是主键；移动文件保持 ID 和平台映射。
- 数据库以 `(repository_id, article_id)` 唯一定位文章。
- 主站以 slug 定位公开 URL，数据库另存历史 slug 以支持重定向。
- 外部映射以 `(article_id, platform_account_id)` 定位，路径、标题和 slug 均不参与匹配。

## 主站同步与部署流程

```text
push / PR merge / 定时校准
        │
        ▼
验证来源并规范化目标 commit
        │
        ▼
仓库任务串行获取最新发布分支
        │
        ▼
生成不可变内容快照并校验
        │
        ├── 失败：记录源 commit 和错误，保留旧站
        │
        ▼
构建候选版本
        │
        ├── 失败：记录构建日志，保留旧站
        │
        ▼
原子切换公开版本并更新部署记录
        │
        ▼
按文章分发意图生成或更新平台任务
```

### 事件处理规则

1. Webhook 验签并保存事件 ID，用于去重和排查。
2. 事件只作为“仓库可能变化”的通知，最终以发布分支实际 HEAD 为准。
3. 同仓库任务串行执行；等待期间出现多个事件，可收敛到最新 commit。
4. 定时校准比较远端 HEAD 与最近处理记录，发现差异即补建任务。
5. 定时校准同时扫描计划发布时间已到期的最新内容快照；即使没有新 commit，也触发所需构建和后续分发。
6. 部署成功和索引更新必须能够分别恢复，不能用一次长事务包裹构建和网络调用。
7. 已完成部署的 commit 再收到相同事件时不重复部署，但计划发布和重试产生的状态变化必须单独判断，不能仅按 commit 跳过。

## 发布状态模型

避免用一个 `status` 覆盖所有维度：

- **内容生命周期**：`draft → published → archived`，来自 Git。
- **部署状态**：`queued → building → succeeded/failed`，来自主站部署记录。
- **分发状态**：`pending → running → succeeded/failed/manual_required`，来自平台任务。
- **远端发布状态**：平台实际返回的草稿、已发布、已下架等状态，按适配器能力记录。

文章页面上的“已发布”必须明确指内容生命周期；是否已在主站可见、是否已同步到某平台分别展示。

## Decap 集成

### 配置映射

Decap collection 与仓库协议保持一致：

- `folder` 指向内容根目录或明确的分类目录。
- Front Matter 字段对应稳定 ID、标题、slug、状态和分发配置。
- 媒体字段生成仓库内可移植的相对路径。
- 预览只用于编辑辅助，最终展示以主站构建结果为准。
- 新建文章必须生成 ID；不能依赖作者手工填写。

Decap 的标准集合通常按固定目录配置。若任意嵌套目录不能被单个集合完整表达，应采用按分类声明集合或定制集合，不能悄悄丢失未配置目录中的文章。

### 认证与提交

- Decap 通过 GitHub backend 和 OAuth/App 访问私有仓库，不使用部署服务器 SSH 私钥。
- 首版是否要求所有编辑者拥有仓库写权限取决于认证拓扑，必须在环境设计中验证。
- 后端只获得目标仓库的最小权限。
- 发布分支受保护时采用工作分支与 PR，不让 CMS 绕过分支保护。
- 冲突时提示重新读取和比较，不在服务端自动接受远端覆盖或本地覆盖。

## 自研编辑器演进

自研编辑器与 Decap 必须使用同一仓库协议和内容校验器。建议演进顺序：

1. 只读文章与发布状态界面。
2. 独立编辑界面，保存时携带基准 blob/commit SHA。
3. 冲突比较、历史差异和回滚。
4. 图片粘贴、资源管理和完整预览。
5. 完成编辑体验与权限验证后，按分类逐步停用 Decap 入口。

Git 提交仍由服务端或 GitHub App 完成；浏览器不持有部署私钥，也不直接访问本地文件系统。

## 多平台任务设计

### 任务身份

每个任务至少包含：

```text
repository_id
article_id
platform_account_id
operation          # create_draft | publish | update | unpublish
source_commit
desired_content_hash
status
attempt_count
remote_object_id
remote_url
last_error
```

为同一文章、账号和操作建立合适的活动任务约束，防止工作进程并发创建重复远端对象。远端对象映射在调用创建接口前持久化任务，在返回后立即保存远端 ID。

### 执行步骤

```text
锁定任务
  → 读取指定源快照
  → 校验平台能力
  → 转换正文和元数据
  → 上传图片等资源
  → 检查已有远端映射
  → 创建或更新
  → 保存远端 ID / URL / 状态
  → 释放锁
```

创建请求超时但结果未知时，任务进入可诊断状态。若平台支持按客户端标记查询则先查询；不支持时转人工核对，不能盲目重试创建。

### 重试与降级

- 限流、临时网络故障：有限次数指数退避，尊重平台重试时间。
- 认证失败：暂停该账号任务，修复凭据后恢复。
- 内容不支持：标记校验错误，不重试。
- 平台无写入 API：导出适配后的 HTML/Markdown/资源包，人工发布后登记 ID 和 URL。
- 外部更新和下架均需独立审计，默认不跟随主站删除而远端删除。

## 数据分类与存储

Git 保存：正文、媒体、发布生命周期、公开元数据、非敏感分发意图。

状态存储保存：内容索引、已处理 commit、部署记录、任务、远端映射、账号配置引用和审计记录。

密钥存储保存：OAuth/App 私密材料、SSH 私钥、第三方访问令牌和加密密钥。

索引损坏时应能从 Git 重建；远端映射和审计记录应单独备份，不能假设可从文章正文恢复。

## 安全设计

- 所有管理接口执行认证与角色授权，公开站不挂载管理接口。
- Webhook 使用原始请求体验签并防重放，仓库和分支均在允许列表中。
- SSH 使用限定仓库的 Deploy Key；只读同步与需要写入的凭据分开。
- Git 操作使用固定参数和受控工作区，防止参数注入、路径穿越和不受控子模块/ hooks 执行。
- 内容构建视为处理不可信输入，限制资源、网络和执行权限。
- 第三方凭据加密，日志与错误界面脱敏。
- 审计记录不可由普通编辑者修改。

## 实施顺序

### 阶段 0：仓库与规则确认

- 获取匿名化目录和 metadata 样本。
- 固定 Front Matter、状态、分类和 slug 语义。
- 明确首个平台及审核流程。
- 为现有文章设计 ID 回填和元数据迁移。

### 阶段 1：主站闭环

- 实现仓库同步、内容校验、静态构建和原子部署。
- 接入 Webhook 与定时校准。
- 建立部署记录和基础公开页面。
- 验证草稿、定时发布、构建失败和漏事件场景。

### 阶段 2：Decap 后台

- 配置 collection、字段、媒体和 GitHub 认证。
- 接入角色入口和提交冲突提示。
- 验证 Decap 与 Git/其他客户端提交走相同发布链路。

### 阶段 3：首个分发适配器

- 建立任务、账号、远端映射和审计模型。
- 实现一个具备官方写入 API 的平台。
- 完成转换预览、资源上传、幂等、重试和人工核对流程。

### 阶段 4：扩展与体验

- 按优先级增加适配器及手动导出模式。
- 增加差异比较、回滚、PR 预览和自研编辑器。
- 根据运行指标优化增量构建和任务调度。

## 验证策略

- **仓库协议测试**：合法/非法 Front Matter、重复 ID、移动目录、缺图和恶意路径。
- **同步测试**：重复 Webhook、乱序事件、漏事件、连续 push 和服务重启。
- **部署测试**：构建失败保留旧站、重复 commit 不重复部署、可回滚。
- **编辑测试**：Decap 实际提交到私有测试仓库，旧稿冲突不会覆盖新稿。
- **适配器契约测试**：统一输入转换、认证、创建、更新、限流和超时。
- **端到端测试**：从在线编辑到主站可见，再到外部平台结果可追踪。
- **安全测试**：越权、Webhook 伪造、路径注入、日志泄密和构建隔离。

具体测试框架和命令在技术选型 ADR 接受后补充；验收必须使用真实私有测试仓库及目标平台测试账号，而不只验证模块导入或静态编译。
