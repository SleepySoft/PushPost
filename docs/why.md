# Why：为什么建设 PushPost

## 背景

文章已经按目录组织在 GitHub 私有仓库中，仓库另有 metadata 用于描述发布状态。当前内容具备版本管理基础，但从一次文章修改到主站上线、再到其他平台发布，仍缺少统一且可靠的自动化流程。

系统需要同时服务两类工作：

- **内容生产**：登录后在线编写、预览、保存和提交 Markdown，保留 Git 历史。
- **内容交付**：自动同步私有仓库，按发布配置上线主站，并向其他平台可追踪地分发。

## 问题

1. **内容分散**：若主站、后台和各平台分别保存正文，很快会出现版本不一致。
2. **发布语义模糊**：草稿、已提交、已部署、已同步到外部平台是不同状态，不能用一个布尔值表达。
3. **同步不可靠**：仅依赖 Webhook 会受丢事件、服务宕机和网络失败影响；仅依赖轮询则延迟较高。
4. **在线编辑容易覆盖他人修改**：浏览器中的旧内容不能直接无条件覆盖仓库新内容。
5. **平台差异明显**：各平台在认证、正文格式、图片、更新能力和发布接口上并不一致。
6. **现成 CMS 边界有限**：Decap 能解决 Git 内容管理，但不等于完整的部署、任务调度和多平台发布系统。

## 为什么选择自研 + Decap

Decap 已提供 Git 后端、内容列表、字段表单、基础 Markdown 编辑和媒体管理。直接采用可以缩短第一版交付时间，避免先开发一套通用 CMS。

自研部分则保留核心业务控制权：

- 仓库同步和发布规则。
- 内容校验、索引和构建触发。
- 发布任务、重试、幂等和审计。
- 多平台转换与适配。
- 后续高级编辑体验。

二者通过 Git 仓库解耦。未来替换编辑器时，发布链路不需要重写。

## 目标

- Git 中的任何合法变更都能以可重复、可补偿的方式进入发布流程。
- 作者可以在线完成从新建文章到提交发布的主要操作。
- 读者只看到符合发布条件且构建成功的内容。
- 每次外部分发都能回答：发布了哪个版本、到了哪里、结果如何、失败原因是什么。
- 单个平台或单次部署失败不会破坏已有线上版本，也不会造成重复文章。
- 核心文章始终可由普通 Git 工具读取、迁移和备份。

## 非目标

- 不把 PushPost 做成通用数据库 CMS 或多人实时协同文档工具。
- 不把第三方平台变成正文事实源，也不默认反向同步平台修改。
- 不承诺所有平台都能全自动发布；能力取决于官方接口和账号权限。
- 不在第一版实现复杂的企业审批、细粒度栏目权限或商业化能力。
- 不用自研编辑器阻塞首版上线。

## 设计原则

### 内容可追溯

文章、配置和提交均可通过 Git 历史追踪。每篇内容使用稳定 ID，移动目录或修改 slug 不应丢失平台关联。

### 期望状态与运行状态分离

Git 表示“作者希望怎样发布”；数据库表示“系统实际执行到哪里”。平台凭据、错误日志、任务锁等运行数据不写入文章仓库。

### 失败隔离

主站、每个平台账号和每篇文章分别执行、分别记录结果。外部平台失败不回滚已经成功的主站部署。

### 至少一次执行，业务效果幂等

任务系统允许重试和重复投递，通过文章 ID、目标账号、操作和内容版本等信息避免重复创建或重复副作用。

### 渐进替换

先复用 Decap 的通用 CMS 能力，再按实际痛点替换编辑界面。仓库格式和发布 API 是稳定边界，UI 不是。

### 明确降级

无法自动发布时，提供可导出内容和人工登记结果的入口，不通过不稳定的模拟登录伪装成自动同步。
