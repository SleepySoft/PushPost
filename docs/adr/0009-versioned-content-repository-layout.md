# ADR-0009：采用版本化的文章目录与元数据协议

- 日期：2026-10-26
- 状态：Proposed

## 背景

仅规定“文章是 Markdown”不足以保证 Decap、自研同步服务和外部平台得到一致结果。文章图片、目录分类、重命名、平台目标和现有中央 metadata 都需要明确归属，否则容易形成路径约定混乱和文章元数据双写。

## 决策

定义版本化内容仓库协议 v1：

- 使用 `content/<category>/<article>/index.md`，每篇文章一个目录，资源保存在该目录 `assets/` 中。
- v1 分类为一级目录，文章主分类由目录决定，不重复保存 category 字段。
- `metadata/webpub.yml` 保存协议版本和站点默认值。
- `metadata/categories.yml` 保存分类稳定 ID、目录和展示配置。
- `metadata/platforms.yml` 保存平台目标的非敏感配置与默认值。
- `metadata/redirects.yml` 保存到文章稳定 ID 的历史路径重定向。
- 文章级元数据只保存在 Front Matter；不建立新的中央逐文章 metadata。
- 未知字段、无效路径、重复 ID、缺失资源和无效目标在候选构建阶段阻断发布。
- 现有仓库通过可审查的一次性迁移进入协议，不长期维持双格式写入。

完整字段和语义见 [内容仓库与 Metadata 设计](../content-repository.md)。

## 后果

- 文章与资源可整体移动，目录含义清晰，Decap 可按分类配置 collection。
- 统一 schema 使 Git 客户端、Decap 和自研服务可以共享验收规则。
- 现有文章需要目录和资源迁移，不能零成本接入。
- 一级分类不支持深层目录树；未来扩展必须升级协议并验证 Decap。
- 严格校验会使包含旧格式或字段拼写错误的提交无法上线，这是有意的安全行为。
- 媒体路径和嵌套 entry path 需要用 Decap 实际验证，必要时做受控定制。

## 备选方案

- **每篇一个 Markdown + 全局媒体目录**：迁移较简单，但文章与资源容易失联。
- **任意深度目录自动分类**：灵活，但 CMS 配置、路由和迁移语义更复杂，v1 不采用。
- **中央 metadata 保存所有文章字段**：便于集中查看，但与 Front Matter 双写会产生冲突。
- **宽松忽略未知格式和字段**：兼容性较好，但可能静默错误发布，拒绝。
