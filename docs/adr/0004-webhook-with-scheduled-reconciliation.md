# ADR-0004：Webhook 与定时校准双通道同步

- 日期：2026-10-26
- 状态：Proposed

## 背景

Webhook 能提供低延迟通知，但可能丢失、重复、乱序或在服务不可用时失败。仅轮询可靠性和延迟又不理想。同步还必须允许任务合并和服务重启恢复。

## 决策

使用 GitHub Webhook 作为主要触发器，定时校准作为补偿。Webhook 在验签和过滤后只表达“仓库可能变化”，实际处理以发布分支远端 HEAD 为准。

同仓库任务串行；连续事件可合并到最新 commit。定时任务比较远端 HEAD 和最近处理记录，补上遗漏变更，并扫描计划发布时间已到期的最新内容快照。因此，没有新 commit 的计划发布也能执行。事件 ID 用于观测去重；部署幂等同时考虑源 commit 和计划发布时间等生效条件，不能只按 commit 跳过。

## 后果

- 重复或乱序事件不会直接决定错误发布顺序。
- Webhook 整体失效时仍能自动恢复，延迟取决于校准周期。
- 需要保存处理进度，并防止并发 worker 操作同一工作区。
- 合并事件意味着中间 commit 不一定单独构建，但最终 HEAD 必须完整发布。

## 备选方案

- **仅 Webhook**：实现简单但不能保证最终一致，拒绝。
- **仅轮询**：可作为最小降级手段，但常态延迟和 API 开销较高。
- **每个事件严格逐个构建**：保留所有中间版本，但成本高且可能发布已被取代的内容。
