# What：产品范围与需求

## 用户与角色

| 角色 | 主要能力 |
| --- | --- |
| 读者 | 浏览、搜索和分享已发布内容，无需登录 |
| 编辑者 | 新建、编辑、预览和提交文章，管理文章媒体 |
| 发布者 | 审核或发布内容，触发外部分发，重试失败任务 |
| 管理员 | 管理用户、仓库、平台账号和系统配置，查看审计记录 |

第一版可以由同一管理员承担编辑者和发布者角色，但权限模型不能假设永远只有一个用户。

## 核心用户流程

### 编写并发布到主站

1. 编辑者登录后台，新建或选择文章。
2. 编辑正文和元数据，插入图片并预览。
3. 保存为草稿，系统提交到 Git。
4. 发布者将文章标记为已发布，或按约定审核并合并变更。
5. 同步服务获取新 commit，校验内容并构建主站。
6. 部署成功后展示当前版本；失败时保留旧站并报告原因。

### 分发到其他平台

1. 发布者为文章选择一个或多个平台账号及发布方式。
2. 系统显示转换校验结果，并创建独立分发任务。
3. 适配器上传资源，创建或更新平台草稿/文章。
4. 系统保存平台文章 ID、URL、内容版本和执行结果。
5. 失败任务可重试；需要人工处理的平台提供导出和结果登记。

## 功能需求

### 内容仓库

- 必须支持 GitHub 私有仓库和指定发布分支。
- 必须按目录形成默认分类，目录移动不能改变文章稳定 ID。
- 必须读取现有 metadata；兼容规则在获得实际样本后确定。
- 必须支持 Markdown、Front Matter 和仓库内图片。
- 必须检测重复文章 ID、重复 slug、非法状态和缺失引用。
- MDX、公式、脚注等扩展语法必须显式声明支持范围，不能静默渲染错误。

### 公开网站

- 只展示 `published` 且已到发布时间的文章。
- 提供分类、文章详情、标签、归档、RSS 和基础 SEO 元数据。
- URL 由稳定 slug 生成；slug 变化必须可追踪，重定向策略由实现阶段确定。
- 构建失败不得替换当前可用版本。
- 文章归档后从公开列表和详情中移除或下架，但保留 Git 历史。
- 搜索、阅读统计和评论不属于首版必需能力。

### 在线编辑

首版由 Decap 提供：

- 登录、文章列表、字段编辑、Markdown 编辑和预览。
- 新建、修改和删除文章，以及媒体上传。
- 按配置映射文章目录、Front Matter 和媒体路径。
- 保存后向指定仓库与分支提交变更。

自研编辑器是后续需求，目标能力包括源码/所见即所得模式、浏览器自动暂存、图片粘贴、差异比较、版本回滚和冲突处理。是否及何时替换 Decap 以实际编辑痛点为依据。

### 保存与发布

- 保存草稿与正式发布必须是两个清晰操作。
- 在线提交必须检测基准版本冲突，禁止无提示覆盖他人的新提交。
- 不允许将每次按键或浏览器自动暂存变成 Git commit。
- 发布必须对应一个确定的 Git commit。
- 需要审核时使用分支和 Pull Request；合并后才进入发布分支。
- 删除和批量发布必须具有确认与审计记录。

### 自动同步与部署

- 接收并验证 GitHub Webhook，按仓库和分支过滤事件。
- 使用 SSH 在受控工作区拉取内容，不接受用户提交任意 Git 命令或路径。
- 同一仓库同步任务必须串行，且可合并连续 push 到最新目标 commit。
- Webhook 丢失或服务重启后，定时校准能发现遗漏变更。
- 每次部署记录源 commit、开始/结束时间、状态和错误摘要。
- 重复处理同一 commit 必须得到一致结果，不产生额外外部文章。

### 多平台分发

- 每篇文章可配置多个目标，每个目标独立指定草稿或发布模式。
- 每个平台以适配器实现认证、校验、转换、资源上传、创建、更新和结果查询。
- 任务必须支持待执行、执行中、成功、失败和需人工处理等状态。
- 自动重试仅用于可恢复错误，并使用有限次数和退避策略。
- 创建任务必须具备幂等保护；超时后必须先查询或核对远端结果再决定是否重建。
- 内容更新优先更新既有平台文章，不重复创建。
- 主站文章删除或归档默认不删除外部平台文章，外部下架必须显式触发。
- 不支持自动写入的平台提供格式导出和人工结果登记。
- 平台令牌加密存储，日志不得泄露令牌、Cookie 或私有正文。

### 管理与可观测性

- 展示文章的主站状态及各目标平台状态。
- 提供按文章、平台和状态筛选的任务记录。
- 支持手动重试、取消未开始任务和查看错误详情。
- 记录登录、提交、发布、下架、重试和配置修改等审计事件。
- 提供同步延迟、部署失败、任务积压和平台失败率等基础指标。

## 内容仓库与元数据需求

完整协议见 [内容仓库与 Metadata 设计](content-repository.md)，核心约束如下：

- 文章采用 `content/<category>/<article>.md`，资源保存在所属分类的 `assets/` 中，不强制创建文章目录。
- v1 机械使用一级目录分类，目录名直接用于展示；不维护分类 ID、注册表或分类 metadata。
- 文章通过稳定 `id` 关联部署和平台记录，路径与 slug 都不是永久身份。
- `status` 限定为 `draft`、`published`、`archived`；`published_at` 支持立即发布和计划发布。
- Front Matter 是文章级元数据的唯一保存位置，中央 metadata 只保存仓库默认值、平台目标和重定向配置。
- `distribution` 表示分发意图，不保存远端文章 ID、任务状态或错误日志。
- 平台凭据只保存于服务端密钥存储，仓库内仅保存逻辑引用。
- 现有 metadata 通过显式迁移进入协议，冲突必须人工处理，不长期双写或隐式合并。

## 非功能需求

- **可靠性**：服务重启不丢任务；失败可恢复；重复事件无副作用。
- **安全性**：后台认证、角色授权、Webhook 验签、最小仓库权限和凭据加密。
- **可恢复性**：可依据 Git 和平台映射重建索引；主站可回滚到上一成功版本。
- **可维护性**：平台适配器相互隔离，内容格式有版本化校验。
- **可解释性**：每次状态变化都能关联到操作者、源 commit 或任务记录。
- **性能**：普通文章页面可静态生成；同步和分发异步执行，不阻塞公开站访问。

## MVP 验收标准

1. 向私有仓库发布分支提交一篇合法 `published` 文章后，无需手工同步即可在主站看到它。
2. `draft`、未到发布时间或校验失败的文章不会出现在公开站。
3. 停止接收 Webhook 后，定时校准仍能发布遗漏 commit。
4. 新构建失败时旧站保持可访问，并能看到失败部署记录。
5. 编辑者可通过 Decap 登录、编辑并提交文章，修改最终进入同一发布流程。
6. 基于旧版本保存时不会覆盖仓库中的新修改。
7. 一个官方 API 适配器能够创建草稿或文章，并保存远端 ID 和 URL。
8. 同一任务重复投递不会创建重复的平台文章。
9. 某平台失败不影响主站和其他目标，恢复后可独立重试。
10. 任意文章均可查看源 commit、主站部署结果和各平台分发结果。

## 明确后续项

- 自研高级 Markdown 编辑器。
- 多人同时编辑同一文章及实时协作。
- 外部平台修改的反向同步。
- 多仓库、多站点和复杂组织权限。
- 全量评论、统计、订阅和商业运营能力。

## 环境验收与后续确认

技术选型已确定为 Astro、Fastify、SQLite 持久任务和 Node.js/TypeScript；首个官方 API 适配器为 WordPress。文章路由、重定向及显式远端下架规则见 ADR-0011 和管理 API。

以下事项仍需真实环境或内容样本，不阻塞本仓库实现：

1. 现有目录树、旧 metadata 字段语义及迁移映射。
2. 编辑者是否都有 GitHub 账号及仓库写权限，生产 Decap OAuth 如何配置。
3. 生产是否启用分支保护和 Pull Request 审核；当前默认同步指定发布分支。
4. 现有文章是否包含 MDX、公式或自定义短代码；协议 v1 仅启用 GFM。
5. 生产部署主机、真实 SSH/HTTPS、备份及 hosted 平台测试账号。
